## Contribuer au code {#contributing-to-the-code}

Merci de lire les [lignes directives de la contribution](https://github.com/ccbogel/QualCoder/blob/master/docs/CONTRIBUTING.md).

### Règles clés en bref {#key-rules-at-a-glance}

- **Choisir d'abord un ticket (issue).** Recherchez un ticket existant ou créez-en un, et commentez-le avant d'ouvrir une Pull Request. Attendez que le ticket vous soit assigné avant de commencer à travailler.
- **Une Pull Request, un seul commit.** Regroupez votre travail en un seul commit avec un message descriptif reflétant vos changements.
- **Nommage.** Créez une branche dédiée, nommée en fonction du ticket traité.
- **Licence.** En soumettant une Pull Request, vous placez votre contribution sous la licence LGPLv3 du projet (« Inbound = Outbound »).

### Contributions assistées par l'IA {#ai-assisted-contributions}

Il est possible d'utiliser des outils d'IA pour assister vos contributions, mais vous restez pleinement responsable de tout ce que vous soumettez.

- **Comprendre** : vous devez être en mesure d'expliquer chaque ligne de votre code.
- **Tester** : le code généré par l'IA doit passer tous les tests et vérifications de sécurité.
- **Déclarer** : indiquez un niveau d'assistance IA (0–5) dans le modèle de Pull Request.
- **Assumer** : vous êtes l'auteur. Si une personne relectrice demande « pourquoi ? », c'est vous qui répondez — pas l'IA.

Les outils d'IA ne doivent **pas** être utilisés pour corriger les tickets étiquetés `good first issue`. Ils existent pour l'apprentissage humain.


## Contribuer à la traduction {#contribute-to-the-translation}
### Traduire la documentation {#translate-the-documentation}

Il est possible de traduire la documentation, en créant / modifiant les fichiers markdown dans docs/doc dans [le dépôt du site internet](https://github.com/QualCoder-Org/qualcoder-org.github.io).

### Traduire le logiciel {#translate-the-software}

QualCoder gère la fonctionnalité multilingue grâce à deux types de fichiers de traduction :

- Les fichiers Gettext (.po ou . mo), qui contiennent la traduction du logiciel ;
- Les fichiers linguistiques QT (fichiers .ts ou .qm) correspondant à l’interface.

Pour traduire :

 1. Créer un fichier langue (lorsqu’il n’existe pas) avec cette commande : ```python rebuild_lang.py --create --lang CODE_LANGUE``` Il est à noter que le nom de vos fichiers langues doit respecter le format [ISO 639-1](https://fr.wikipedia.org/wiki/Liste_des_codes_ISO_639-1).
 2. Si un fichier linguistique existe déjà, vous pouvez mettre à jour les traductions ```python rebuild_lang.py --update --lang CODE_LANGUE```.
 3. Il est possible d’éditer les traductions des fichiers .po et .ts dans le dossier src/i18n à l’aide du logiciel [Poedit](https://poedit.net/).
 4. Une fois le travail terminé, compiler au format machine, à l’aide de cette commande : ```python rebuild_lang.py --compile --lang CODE_LANGUE```.


Glossaire concernant la traduction, afin d’avoir une cohérence dans la traduction :

- Speakers : Intervenant⋅es
- Coder : Codeur·euse
- Case : cas
- Transcript : Retranscription
- Counts : occurrences
- Automatic coding : autocodage
- Mark : Surligner
- Prompt AI : [Instruction](https://www.legifrance.gouv.fr/jorf/id/JORFTEXT000050185686)
- Stop words: mots vides
- Codebook : Grille de codage
- Red weak : Protanomalie
- Red blind : Protanopie
- Green weak : Deutéranomalie
- Green blind : Deutéranopie
- Pie charts : Diagrammes circulaires
- Bar charts :  Graphique à barres

## Contribuer autrement : tutoriels, vidéos et études de cas {#tutorials}

Toutes les contributions à QualCoder ne se résument pas à une ligne de code. Le projet se nourrit également de l’engagement de personnes qui expliquent le logiciel à d’autres : en rédigeant des tutoriels, en réalisant des vidéos ou en partageant leur expérience et leurs études de cas. Ces contributions permettent aux nouveaux utilisateurs de voir concrètement comment le logiciel est utilisé, dans une discipline, un langage ou un contexte de recherche donnés, ce qu’aucun manuel de référence ne peut couvrir. Si vous utilisez QualCoder dans votre travail, vous avez sans doute quelque chose à transmettre.

### Rédiger un tutoriel {#writing-tutorial}

Un bon tutoriel ne se contente pas d’énumérer les fonctionnalités : il guide l’utilisateur à travers un exemple du début à la fin, du fichier brut au résultat d’analyse. Voici quelques sujets utiles :

- l’installation et le premier lancement (sous Windows, macOS, GNU/Linux ou à partir du code source) ;
- la création d’un projet et l’organisation des fichiers, des cas et des attributs ;
- le codage de texte, d’images, d’audio et de vidéo ;
- l’importation d’enquêtes ;
- les requêtes, les rapports, les comparaisons entre codeurs et les visualisations ;
- les fonctionnalités récentes, en particulier l’analyse assistée par l’IA.

Pour que ce tutoriel reste utile au fil du temps :

- **Précisez le contexte** : version de QualCoder, système d’exploitation, langue de l’interface, afin que le tutoriel reste compréhensible à mesure que l’interface évolue.
- **Travaillez sur des données d’exemple** : un petit corpus fictif est plus pédagogique qu’un projet réel et évite les problèmes de confidentialité.
- **Illustrez les étapes clés** à l’aide de captures d’écran et d’actions précises (clics, menus, raccourcis), y compris les difficultés rencontrées lors des premiers pas.
- **Rédigez dans votre propre langue** : les ressources dans d’autres langues que l’anglais sont particulièrement bienvenues.

### Réalisation de vidéos {#producing-videos}

La vidéo montre directement les gestes à effectuer : création d’un projet, sélection d’un extrait, codage, comparaison, exportation. Pour une vidéo efficace :

- indiquez dès le début la version utilisée et l’objectif ;
- privilégiez les clips courts et ciblés (une tâche, une vidéo), ou des vidéos plus longues divisées en chapitres ;
- veillez à la qualité du son et à la lisibilité à l’écran, et ajoutez des sous-titres si possible ;
- publiez librement (YouTube, PeerTube…) et prévenez l’équipe afin que la vidéo puisse être répertoriée sur la page des tutoriels vidéo du wiki.

## Partager votre expérience ou une étude de cas {#share-experience}

Racontez comment vous avez concrètement utilisé QualCoder, que ce soit lors d’un travail de terrain, d’une thèse ou d’un atelier : cela répond à la question que tout chercheur se pose avant d’adopter un outil : « cet outil a-t-il déjà été utilisé dans un contexte similaire au mien ? ». Quelques pages décrivant votre discipline, vos données, votre méthodologie, les fonctionnalités sur lesquelles vous vous êtes appuyé(e) et, en toute honnêteté, les limites rencontrées constituent déjà une contribution précieuse. Les comparaisons avec des logiciels commerciaux (NVivo, ATLAS.ti, MAXQDA) et les retours d’expérience issus d’ateliers pédagogiques sont également très recherchés.

Deux mises en garde : **anonymisez toutes les données réelles** et vérifiez que votre cadre de consentement autorise la publication ; et **citez correctement le logiciel**, en mentionnant la version utilisée (le dépôt GitHub fournit les informations de citation).

Votre ressource sera ensuite répertoriée dans la documentation, afin que le plus grand nombre possible de personnes puisse en bénéficier. Et si, au cours de la rédaction, vous identifiez des améliorations possibles pour le logiciel ou sa documentation, ces retours constituent également une contribution : ils alimentent la feuille de route du projet.
