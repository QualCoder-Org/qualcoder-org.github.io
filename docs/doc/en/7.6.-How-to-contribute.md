# How to contribute


## Contributing to the code {#contributing-to-the-code}

Please read the [contribution guidelines](https://github.com/ccbogel/QualCoder/blob/master/docs/CONTRIBUTING.md)

### Key rules at a glance {#key-rules-at-a-glance}

- **Pick an issue first.** Look for an existing issue or create one, and comment on it before opening a Pull Request. Wait until the issue is assigned to you before starting work.
- **One Pull Request, one commit.** Squash your work into a single commit with a descriptive message that reflects your changes.
- **Naming.** Create a dedicated branch named after the issue you are addressing.
- **License.** By submitting a Pull Request, you license your contribution under the project's LGPLv3 license ("Inbound = Outbound").

### AI-assisted contributions {#ai-assisted-contributions}

You may use AI tools to assist your contributions, but you remain fully responsible for everything you submit.

- **Understand it**: you must be able to explain every line of your code.
- **Test it**: AI-generated code must pass all tests and security checks.
- **Disclose it**: pick an AI assistance level (0–5) in the Pull Request template.
- **Own it**: you are the author. If a reviewer asks "why?", you answer — not the AI.

AI tools must **not** be used to fix issues labelled `good first issue`. These exist for human learning.


## Contribute to the translation {#contribute-to-the-translation}
### Translate the documentation {#translate-the-documentation}

You can translate the documentation by creating/modifying the markdown files in docs/doc in [the website repository](https://github.com/QualCoder-Org/qualcoder-org.github.io).

### Translate the software {#translate-the-software}

QualCoder supports multilingual functionality using two types of translation files:

- Gettext files (.po or .mo), which contain the software translation;
- QT language files (.ts or .qm) corresponding to the user interface.

To translate:

 1. Create a language file (if one does not already exist) using this command: ```python rebuild_lang.py --create --lang LANGUAGE_CODE``` Please note that the names of your language files must comply with the [ISO 639-1](https://fr.wikipedia.org/wiki/Liste_des_codes_ISO_639-1) format.
 2. If a language file already exists, you can update the translations using ```python rebuild_lang.py --update --lang LANGUAGE_CODE```.
 3. You can edit the translations of the  .po and .ts files in the src/i18n folder using the [Poedit](https://poedit.net/) software.
 4. Once the work is complete, compile to machine format using this command: ```python rebuild_lang.py --compile --lang LANGUAGE_CODE```.

## Contributing in other ways: tutorials, videos, and case studies

Not every useful contribution to QualCoder is a line of code. The project also thrives thanks to the people who take the time to explain the software to others: by writing tutorials, producing videos, or sharing their experience and case studies. These contributions are precious, because they let a new user see concretely how the software is used, in a given discipline, language, or research setting, something no reference manual can cover on its own. If you use QualCoder in your work, you probably have something to pass on, and this page explains how.

### Writing a tutorial

A good tutorial does not list features: it walks through an example from start to finish, from the raw file to the analysis result. Particularly useful topics to cover:

- installation and first launch (Windows, macOS, GNU/Linux, or from source);
- creating a project and organising files, cases, and attributes;
- coding text, images, audio, and video;
- importing surveys and processing questionnaire data;
- queries, reports, inter-coder comparisons, and visualisations;
- recent features, especially AI-assisted analysis, for which the documentation evolves quickly.

A few recommendations to keep your tutorial useful over time:

- **State the context**: QualCoder version, operating system, interface language. The software evolves quickly; a dated, versioned tutorial remains interpretable even after the interface changes.
- **Work on sample data where possible**: a small fictional corpus is more pedagogical than a real project, and avoids any confidentiality issues.
- **Illustrate the key steps** with screenshots, and describe the actions precisely (clicks, menus, shortcuts), including the stumbling blocks you hit when you were starting out.
- **Write in your own language**: English-language resources are the most abundant; tutorials in French, Spanish, German, Portuguese, or other languages are especially welcome.

### Producing videos

Video is the most direct format for showing the gestures: creating a project, selecting an excerpt, coding, comparing, exporting. In a few minutes the user sees what lengthy documentation would laboriously describe.

For an effective video:

- announce the version used and the tutorial's goal right at the start;
- favour short, focused videos (one task, one video), or a chaptered table of contents for longer presentations;
- take care with audio quality and on-screen readability, and add subtitles where possible, which make the video accessible and translatable;
- publish freely (YouTube, PeerTube...) and let the project team know about your video so it can be listed on the wiki's Vidéo tutorial's page.

## Sharing your experience or a case study

Telling the story of how you actually used QualCoder, in fieldwork, a thesis, a dissertation, or a workshop, answers the question every researcher asks before adopting a tool: "has this already been used, in a context like mine?". A case study does not need to be a methodological article: a few pages describing your discipline, your data, your methodology, the QualCoder features you relied on, and, honestly, the limitations you encountered, are already a valuable contribution. Comparisons with commercial software (NVivo, ATLAS.ti, MAXQDA) and accounts from teaching workshops are also highly sought after, as shown by the guides some universities have produced around QualCoder.

Two points of caution:

- **Confidentiality**: if you show real data, anonymise it and check that your study's consent framework allows this kind of publication;
- **Traceability**: mention the version used and cite the software properly in your work (the GitHub repository provides the citation information).

## How to submit your contribution

No technical account or pull request is needed for these contributions. The simplest way:

1. **Open an issue** on the [QualCoder GitHub repository](https://github.com/ccbogel/QualCoder) describing what you would like to share; the team will tell you the best way to integrate it (wiki, blog, project website);
2. **Or report it directly** to the team via the blog or the project's channels, especially if your content is already published online.

Your resource will then be listed in the documentation, so that as many people as possible benefit from it. And if, while writing, you discover ways the software or its documentation could be improved, that feedback is a contribution too: it feeds the project's roadmap.
