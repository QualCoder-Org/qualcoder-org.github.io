## Contributing to the code {#contributing-to-the-code}

Please read the [contribution guidelines](https://github.com/ccbogel/QualCoder/blob/master/docs/CONTRIBUTING.md)

### Key rules at a glance {#key-rules-at-a-glance}

- **Pick an issue first.** Look for an existing issue or create one, and comment on it before opening a Pull Request. Wait until the issue is assigned to you before starting work.
- **One Pull Request, one commit.** Squash your work into a single commit with a descriptive message that reflects your changes.
- **Naming.** Create a dedicated branch named after the issue you are addressing.
- **License.** By submitting a Pull Request, you license your contribution under the project's LGPLv3 license ("Inbound = Outbound").

### AI-assisted contributions {#ai-assisted-contributions}

You may use AI tools to assist your contributions, but you remain fully responsible for everything you submit.

- **Understand it**: you must be able to explain every line of your code.
- **Test it**: AI-generated code must pass all tests and security checks.
- **Disclose it**: pick an AI assistance level (0–5) in the Pull Request template.
- **Own it**: you are the author. If a reviewer asks "why?", you answer — not the AI.

AI tools must **not** be used to fix issues labelled `good first issue`. These exist for human learning.


## Contribute to the translation {#contribute-to-the-translation}
### Translate the documentation {#translate-the-documentation}

You can translate the documentation by creating/modifying the markdown files in docs/doc in [the website repository](https://github.com/QualCoder-Org/qualcoder-org.github.io).

### Translate the software {#translate-the-software}

QualCoder supports multilingual functionality using two types of translation files:

- Gettext files (.po or .mo), which contain the software translation;
- QT language files (.ts or .qm) corresponding to the user interface.

To translate:

 1. Create a language file (if one does not already exist) using this command: ```python rebuild_lang.py --create --lang LANGUAGE_CODE``` Please note that the names of your language files must comply with the [ISO 639-1](https://fr.wikipedia.org/wiki/Liste_des_codes_ISO_639-1) format.
 2. If a language file already exists, you can update the translations using ```python rebuild_lang.py --update --lang LANGUAGE_CODE```.
 3. You can edit the translations of the  .po and .ts files in the src/i18n folder using the [Poedit](https://poedit.net/) software.
 4. Once the work is complete, compile to machine format using this command: ```python rebuild_lang.py --compile --lang LANGUAGE_CODE```.

## Contributing in other ways: tutorials, videos, and case studies {#tutorials}

Not every contribution to QualCoder is a line of code. The project also thrives on people who explain the software to others: writing tutorials, producing videos, or sharing their experience and case studies. These contributions let new users see concretely how the software is used, in a given discipline, language, or research setting, something no reference manual can cover. If you use QualCoder in your work, you probably have something to pass on.

### Writing a tutorial {#writing-tutorial}

A good tutorial does not list features: it walks through an example from start to finish, from raw file to analysis result. Useful topics include:

- installation and first launch (Windows, macOS, GNU/Linux, or from source);
- creating a project and organising files, cases, and attributes;
- coding text, images, audio, and video;
- importing surveys;
- queries, reports, inter-coder comparisons, and visualisations;
- recent features, especially AI-assisted analysis.

To keep it useful over time:

- **State the context**: QualCoder version, operating system, interface language, so the tutorial stays interpretable as the interface evolves.
- **Work on sample data**: a small fictional corpus is more pedagogical than a real project and avoids confidentiality issues.
- **Illustrate the key steps** with screenshots and precise actions (clicks, menus, shortcuts), including the stumbling blocks you hit when starting out.
- **Write in your own language**: resources other than English are especially welcome.

### Producing videos {#producing-videos}

Video shows the gestures directly: creating a project, selecting an excerpt, coding, comparing, exporting. For an effective video:

- announce the version used and the goal at the start;
- favour short, focused clips (one task, one video), or chapter longer ones;
- take care of audio and on-screen readability, and add subtitles where possible;
- publish freely (YouTube, PeerTube...) and tell the team so it can be listed on the wiki's video tutorials page.

### Sharing your experience or a case study {#share-experience}

Telling how you actually used QualCoder, in fieldwork, a thesis, or a workshop, answers the question every researcher asks before adopting a tool: "has this already been used in a context like mine?". A few pages describing your discipline, data, methodology, the features you relied on, and, honestly, the limitations encountered are already a valuable contribution. Comparisons with commercial software (NVivo, ATLAS.ti, MAXQDA) and accounts from teaching workshops are also highly sought after.

Two cautions: **anonymise any real data** and check that your consent framework allows publication; and **cite the software properly**, mentioning the version used (the GitHub repository provides citation information).

Your resource will then be listed in the documentation, so as many people as possible benefit from it. And if, while writing, you find ways the software or its documentation could improve, that feedback is a contribution too: it feeds the project's roadmap.
